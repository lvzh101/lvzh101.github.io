WSL2 连接 Windows 的 FlClash 代理：配置、验证与排错

最近在 WSL2 里维护 Hexo 博客时，我遇到了 Node.js 下载连接超时的问题。Windows 上已经开启了 FlClash，但 WSL2 里的命令行工具仍然无法稳定访问下载源。

这次我把 WSL2 连接 Windows 代理的过程整理下来，包括临时配置、终端自动加载、开关命令，以及实际连接验证。最终可以在任意目录使用 proxy set、proxy unset、proxy status 和 proxy test 管理代理。

一、我的环境与连接原理

这次实际使用的环境如下：

项目 配置
Windows Windows 10
Linux Ubuntu 24.04，运行于 WSL2
WSL2 网络模式 NAT
Windows 代理软件 FlClash
HTTP／混合代理端口 7890
终端 Bash

本文的地址获取方式适用于 WSL2 的 NAT 网络模式。 如果使用镜像网络，需要根据实际网络情况调整代理地址。

在我的环境中，Windows 系统代理地址是 127.0.0.1:7890。这个地址在 Windows 内指向 Windows 自己，而在 WSL2 的 NAT 网络中，127.0.0.1 指向 WSL2 自己。

因此，WSL2 需要通过 Windows 在虚拟网络中的地址访问代理。我的连接路径是：

十、为什么没有直接修改 sudo 配置

另一个常见思路是让 sudo 保留代理变量，例如调整 sudoers 或使用 sudo -E。

本文使用 APT 专用配置，原因是：

  • APT 可以独立于当前 Shell 的变量工作；
  • 不需要修改系统的 sudo 环境继承策略；
  • 普通终端关闭代理，不会意外影响 APT；
  • 动态发现脚本可以在每次调用时重新获取网关；
  • 配置文件和用途更容易对应。

如果只是临时执行一次，使用前面的两个 Acquire::...::Proxy 命令行选项即可。

十二、如何理解 APT 输出和更新速度

12.1 Hit、Get、Ign、Err 的含义

输出 含义

12.3 可升级包数量为什么从 92 变成 435

apt update 只刷新索引，不安装更新。

表示根据当前可用索引，有 435 个已安装包存在可升级版本。

此前部分软件源更新失败，APT 可能沿用了旧索引。补齐安全更新和 ROS 源后，能发现更多更新，因此可升级数量增加。

这不是刚才已经升级了 435 个包。

十五、使用时需要注意的边界

  • 本文的自动发现方式针对 WSL2 NAT。切换镜像网络或修改路由后，需要重新确认代理地址。
  • Windows FlClash 必须正常运行，且 HTTP／混合代理端口与脚本一致。
  • 开启允许局域网时，防火墙权限尽量限制在需要访问的 WSL 网络范围，避免不必要地暴露代理。
  • 博客和截图中不要公开带用户名、密码或令牌的代理 URL。
  • APT 自动发现只管理 APT 的网络请求，不会自动给软件安装脚本中的 curl、Git、npm 或其他程序配置代理。
  • 原有代理脚本仍可用于普通终端程序；SSH 和 Windows 可执行程序还可能需要各自的配置。
  • 代理成功不代表 WSL 的直接 DNS 已经修复。
  • 不要通过关闭软件源签名校验或 HTTPS 证书校验解决代理问题。
